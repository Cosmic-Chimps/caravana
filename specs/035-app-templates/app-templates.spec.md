# Feature Specification: App templates

**Feature Branch**: `alta/fresh-kestrel-ng5c` (worktree; no feature branch of its own)
**Created**: 2026-11-12
**Status**: Draft
**Input**: CodeAlta task `2026-11-12-11-app-templates-install-a-known-app-in-a-few-fields-4b6w`: install a known
app (a status page, a fediverse server, a database with its admin page) from New app › From a template by
answering two or three questions. A template is a Compose file plus a manifest; installing it is a normal
Compose deploy. The catalog lives in its own repository, `Cosmic-Chimps/caravana-templates`, and each release
of Caravana embeds a copy.

Today a known app needs its Compose file found, an overlay written (domains, health, secrets, backup) and
passwords generated by hand: `deploy/examples/hollo/` and `deploy/examples/codemagic-patch/` each need a
runbook and a script. A template does that work once, for everybody.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Install a known app from the console (Priority: P1)

The owner opens New app › From a template, finds Uptime Kuma in a grid they can search and filter by tag,
types a domain, keeps the suggested name and place, and presses Create. Caravana renders the template's
Compose file and overlay with that domain, deploys it like any Compose app, and opens the app's
Deployments tab. Its volume is backed up on the template's schedule.

**Why this priority**: it is the feature: a visitor's first try of Caravana should not need a Compose file.

**Independent Test**: in the lab, through the console's forms only, install Uptime Kuma with only a domain
typed; it becomes healthy, its service has a `volume` backup policy, and its app record names the template.

**Acceptance Scenarios**:

1. **Given** the embedded catalog, **When** the owner opens New app › From a template, **Then** every
   template that isn't broken and that this Caravana can run is shown as a card (logo or monogram, title,
   one line, tags), and a search for "status" or the tag `monitoring` narrows the grid, without JavaScript.
2. **Given** the Uptime Kuma template, **When** the owner types `status.example.com` and presses Create,
   **Then** an app `uptime-kuma` is created in the chosen place from the rendered file, its first deployment
   starts, and the browser lands on its Deployments tab.
3. **Given** a template input of type `domain`, **When** the owner types `not a domain`, **Then** the form
   comes back with the message at that input, nothing is created, and secret inputs they typed are not
   echoed back.
4. **Given** an app `uptime-kuma` already exists in that place, **When** the owner installs again with the
   same name, **Then** the form says the name is taken and nothing changes.
5. **Given** the domain is already served by another app, **When** the owner installs, **Then** the
   refusal is shown at the domain input, not as a path in a file the owner never saw.

---

### User Story 2 - Passwords Caravana makes and never shows (Priority: P1)

Hollo needs a session secret and a database password used by two services. The template declares them as
generated secrets; Caravana makes them at install with a secure random source and sends them only in the
deploy's overlay, so they go to the secret store and nowhere else.

**Why this priority**: hand-made passwords are the main friction of the runbooks, and a template that
leaked them would be worse than none.

**Independent Test**: install a template whose generated secrets come from a test random source that
yields a sentinel; the sentinel is in the secret store and in no page, API answer, log line, store row,
kept Compose file, deployment record or the SQLite file.

**Acceptance Scenarios**:

1. **Given** the Hollo template, **When** the owner installs it with a domain, **Then** both services get
   the same database password (Hollo's `DATABASE_URL` and Postgres's `POSTGRES_PASSWORD`), Hollo gets a
   64-hex `SECRET_KEY`, both services become healthy, and Postgres has a `postgres` backup policy.
2. **Given** an installed template app, **When** the owner opens Configure or downloads its Compose file,
   **Then** they see the secrets' names and never their values.
3. **Given** a template that puts a generated secret or a secret input into its Compose file, **When**
   the catalog is read, **Then** that template is refused as invalid (it is never offered).

---

### User Story 3 - Install from the API and see what agents can see (Priority: P2)

A script or the Aspire publisher installs a template with one call: the template's name, the app ID and
the inputs. An agent through `caravana mcp` lists the templates and reads one.

**Acceptance Scenarios**:

1. **Given** an API token, **When** a client sends `POST /v1/templates/uptime-kuma/install` with an app ID
   and `{"domain": "status.example.com"}`, **Then** the answer is the same 202 deployment answer
   `deployCompose` gives, and the app record has `template: {name, version}`.
2. **Given** a missing or badly typed input, **When** the client installs, **Then** the answer is 422
   `invalid_field` with `field` `inputs.<name>`.
3. **Given** a deploy token, **When** it calls any template operation, **Then** it gets 403 `token_scope`.
4. **Given** `caravana mcp`, **When** an agent lists tools, **Then** `list_templates` and `get_template`
   are offered without `--allow-actions`, and there is no install tool.

---

### User Story 4 - A catalog that grows without a Caravana release (Priority: P2)

Caravana checks the catalog repository's latest release once a day, as it checks for its own releases: a
`SHA256SUMS` file first, then `catalog.json` only when its sum changed, verified against that sum. A newer
valid catalog replaces the embedded one; the owner can turn checking off and then Caravana makes no
request at all. Offline, or with checking off, the embedded copy is offered.

**Acceptance Scenarios**:

1. **Given** checking is on and the catalog release has a newer version, **When** the check runs, **Then**
   the new catalog is stored and offered, and the page says which version it is and when it was fetched.
2. **Given** a `catalog.json` whose sum doesn't match `SHA256SUMS`, an unknown `format`, or an invalid
   template, **When** the check runs, **Then** nothing changes and the page says the check failed in
   Caravana's words.
3. **Given** checking is off, **When** a day passes or the owner opens the page, **Then** no request is
   made and the embedded (or last stored) catalog is offered.
4. **Given** a template marked `broken` in the catalog, or needing a newer Caravana, **When** the grid is
   drawn, **Then** it isn't offered (the API lists it with its reason, the console leaves it out).

---

### User Story 5 - The catalog's own quality gate (Priority: P2)

The catalog repository's CI renders every template with example inputs through Caravana's own compose
translator and job translator (`caravana template check <dir>`): a refusal or a warning fails the build. Its
release workflow bundles `catalog.json` and `SHA256SUMS`. A script in the repository installs each template
into a running Caravana and waits for healthy (the lab job).

**Acceptance Scenarios**:

1. **Given** a template whose rendered file has `depends_on`, **When** `caravana template check` runs,
   **Then** it fails naming the template and the warning's path.
2. **Given** the embedded catalog in Caravana, **When** `go test ./internal/templates` runs, **Then** every
   embedded template passes the same check and the embedded file matches its `SHA256SUMS`.

### Edge Cases

- A template whose placeholders name no declared input or generated secret is invalid.
- An input value that would change the Compose file's structure (spaces, quotes, `#`, `$`, braces,
  newlines, commas) is refused before rendering; the rendered file is then parsed by the same loader as any
  Compose deploy.
- The logo is an SVG served only as an image, from its own route, with a CSP that runs nothing; a logo with
  script, event attributes, `foreignObject` or external references is refused at catalog read.
- Installing never overwrites: the install is conditional on a new app (as `If-None-Match: *`).
- A failed rollout leaves the app as any failed Compose deploy does, with the template recorded.
- A template app is a normal app afterwards: editing its file, promoting, exporting and deleting work as
  for any Compose app. The recorded template is provenance only: nothing reads it to deploy.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: A template MUST be a Compose file plus a manifest with: name, title, version, description,
  tags, optional logo, upstream link, default app name, optional notes, inputs (typed: `domain`, `email`,
  `text` with a pattern, `secret`), generated secrets (length and alphabet) and the overlay (per service:
  domains, health, secrets, backup). Nothing executable.
- **FR-002**: Rendering MUST be placeholder substitution only (`{{name}}`), with secret-valued names
  (secret inputs and generated secrets) allowed only in overlay secret values.
- **FR-003**: Generated secrets MUST come from `crypto/rand`, MUST travel only in the deploy request's
  overlay, and MUST NOT be stored, logged, shown or returned.
- **FR-004**: Installing MUST be a Compose deploy of a new app (`DeployComposeIfResult` with a new-app
  condition) and MUST record the template's name and version on the app.
- **FR-005**: The API MUST offer `listTemplates`, `getTemplate`, `getTemplateLogo`, `previewTemplate`,
  `installTemplate`, `checkTemplates` and `putTemplateSettings`, in `api/openapi.yaml`, with
  `AppRecord.template`. Deploy tokens are denied by the default deny.
- **FR-006**: The console MUST offer New app › From a template (grid with search and tags), a page per
  template with its inputs and the place, and the catalog's state with Check now and the on/off setting.
  Forms work without JavaScript.
- **FR-007**: Caravana MUST embed a catalog and MAY replace it with a newer verified one fetched from the
  catalog repository's latest release; checking can be turned off and sends no identifying data.
- **FR-008**: `caravana template check <dir>` and `caravana template bundle <dir> <out>` MUST exist for the
  catalog repository's CI and release.
- **FR-009**: The MCP server MUST offer `list_templates` and `get_template` as read tools.

### Key Entities

- **Template**: manifest + Compose text + optional logo; identified by name, versioned.
- **Catalog**: format, version, templates; embedded or fetched.
- **Installed template**: the (name, version) pair on an app.

## Success Criteria *(mandatory)*

- **SC-001**: In the lab, Uptime Kuma installs from New app with only a domain typed, becomes healthy and has
  its volume backup on; no generated secret appears in any page, answer, log or record (sentinel test).
- **SC-002**: In the lab, Hollo installs with only a domain (see research R9 on the admin email), both
  services healthy, and a Back up now of Postgres succeeds.
- **SC-003**: `caravana template check` passes on every template of the catalog repository, in its CI and in
  Caravana's `go test`; with checking off and no network the embedded catalog is offered.
